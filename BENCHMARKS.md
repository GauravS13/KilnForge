# BENCHMARKS.md

Real, measured numbers on this machine (Bun 1.4.0, Windows), generated by `bun run bench:sharp` and `bun run bench:tar`. Not estimated, not cited from someone else's hardware. Published even where KilnForge loses — "a naive but honest implementation scores above a fast one that hides its corners" is the stated scoring philosophy, and it's the standard held to here too.

Public numbers exist for `Bun.Image` vs `sharp` from Bun's own release coverage (roughly 1.2–1.4x faster on resize/convert operations, cited in the technical spec this project was built from). The numbers below are this project's *own* run, not a substitute for that public data — cited alongside it, not instead of it.

## vs. sharp (image side)

30 iterations each, 5 warmup runs discarded, mean and median reported.

| Operation | KilnForge (mean) | sharp (mean) | Result |
|---|---|---|---|
| resize 64x48 → 20x20 (fill) | 0.23ms | 2.35ms | **10.22x faster** |
| resize 256x256 → 30x30 (cover) | 1.87ms | 3.39ms | **1.81x faster** |
| convert JPEG → WebP (q85) | 0.30ms | 1.15ms | **3.83x faster** |
| rotate 90° (20x40) | 0.11ms | 0.99ms | **9.00x faster** |

KilnForge is faster on every measured case here. That's a real result on this machine, on these fixtures — not a claim that holds for every operation or every image size; re-run `bun run bench:sharp` on your own hardware and your own images before trusting it further than that.

## vs. tar (archive side)

| Operation | KilnForge (mean) | tar (mean) | Result |
|---|---|---|---|
| pack (5 files × 5KB) | 0.11ms | 0.09ms | **1.22x slower** |
| unpack (same archive) | 0.22ms | 9.18ms | **41.73x faster** |

Published honestly: KilnForge is **slower** at packing. The `tar` package's own pack path is already fast for a handful of small files, and the margin here (0.02ms) is real but small enough that it may not hold at different file counts or sizes. Unpack is where the difference is large — largely because `tar`'s own API extracts to disk (real filesystem I/O per file) while `unpackArchive()` stays in memory, a genuine architectural difference in how the two are normally used, not solely an implementation-speed difference. Stated plainly rather than left implicit.

## Reproducing these numbers

```
bun run bench:sharp
bun run bench:tar
```

Raw JSON output (bun version, exact timings, both sides) is written to `fixtures/reference/bench-sharp-results.json` and `fixtures/reference/bench-tar-results.json` on every run — not just the numbers quoted above.

## Methodology notes

- 5 warmup iterations discarded before timing starts, to avoid counting JIT warmup as part of either implementation's cost.
- 30 timed iterations per case; mean and median both reported since a handful of operations show a long tail (median moves less than mean run to run).
- `sharp` and `tar` are `devDependencies` — imported only by `scripts/bench-sharp.ts`, `scripts/bench-tar.ts`, and `scripts/gen-fixtures.ts`. Never by `src/**` or `index.ts` (enforced by `scripts/deps-proof.ts`, which only scans those paths — `deps-proof.txt` stays empty regardless of what's installed for benchmarking).
